# СТРУКТУРА — правила работы

Универсальная POS/CRM-система для малого бизнеса (React Native, Expo SDK 56, SQLite + Supabase).
Репозиторий `krokodile7712-del/struktura-app`, ветка `main`.
Владелец — владелец кофейни, без образования в программировании; курирует разработку сам.
Основное устройство — планшет (альбомная ориентация). Телефон — дополнение (принять заказ, посмотреть статистику и т.п.).
Порядок работ: сначала основные баги планшетной версии, потом пересборка мобильного приложения.

## 1. Как работать с владельцем

1. **Только русский язык** — и ответы, и рассуждения. Названия экранов и разделов в тексте — по-русски (Обзор, Касса, Записи, Продажи, Клиенты, Товары, Склад, Финансы, Настройки). Английские имена — только внутри блоков кода.
2. **Просто и коротко.** Владелец не программист: без жаргона, объясняй, что изменено и зачем. Понимай контекст без повторных объяснений.
3. **Сначала обсуждение, потом код.** Для любой новой функции или переделки сначала — наблюдения, допущения, варианты и **полное письменное резюме изменений**. Код пишется только после явного подтверждения. Исключение: владелец прямо сказал «делай» или «исправь сам».
4. **Минимум вопросов.** Вместо вопросов формулируй наблюдения и допущения. Спрашивай только при реальной развилке и не больше одного вопроса за раз.
5. **Честность о состоянии.** Всегда разделяй: что проверено (синтаксис, расчёт, чтение кода), а что нет (работа на устройстве). Не выдавай непроверенное за готовое. Если инструменты заканчиваются на середине большой правки — зафиксируй, что сделано и проверено, а что нет.
6. **Не угадывай причину.** Найди её по коду, скриншоту, видео. Если первое исправление не подтверждено на устройстве — так и скажи. Если не помогло — признай и ищи глубже, а не подгоняй числа.
7. **Работай в отдельной ветке** и открывай пул-реквест. В `main` напрямую не пушить. Владелец принимает пул-реквест и делает `git pull` на планшете.
8. **Одна тема — одна задача.** Не смешивай в одной ветке несвязанные правки.

## 2. Проверки и коммиты

- **Синтаксис — после каждой правки отдельно**, для каждого изменённого файла, через `@babel/parser` (плагин `jsx`). Перед коммитом — проверка **всех** `.js` файлов проекта. Парсер ставь вне репозитория (во временную папку).
- **Не трогать `package.json` и `package-lock.json`** без необходимости: владелец ставит пакеты на планшете, и при `git pull` возникает конфликт. Если пакет нужен — скажи об этом отдельно. Если пакет всё же добавляется — версии берутся из `bundledNativeModules.json` пакета `expo` для текущего SDK (или фиксируются точно), `package.json` и `package-lock.json` обновляются вместе (`npm install --package-lock-only`), а владелец ставит их одной командой `npm install` после `git pull` (не `npx expo install`).
- **Коммиты подробные:** что изменено, почему, найденная причина. Попутно найденные баги — отдельной строкой. В конце — «Не проверено на устройстве: …», если это так.
- **Комментарии в коде — на русском и про «почему»**, а не «что» (так принято в проекте).
- Не коммить токены, ключи и пароли ни в каком виде.

## 3. Минимализм кода

Адаптировано из правил проекта ponytail (MIT, github.com/DietrichGebert/ponytail). Перед написанием кода остановись на первой ступени, которая подходит:
1. Нужно ли это вообще?
2. Нет ли уже в проекте (помощник, компонент, приём)? Используй его.
3. Делает ли это стандартная библиотека или сам язык?
4. Есть ли встроенная возможность платформы (React Native, Expo)?
5. Решает ли это уже установленный пакет?
6. Хватит ли одной строки?
7. Только потом — минимум кода, который работает.

Правила:
- Лесенка работает **после** того, как понял задачу: прочитай код, которого касается правка, и проследи реальный путь данных.
- **Баг чинится в причине.** Найди всех, кто вызывает общую функцию, и исправь её один раз, а не каждое место отдельно (так сделаны окна: общая обёртка вместо правки каждого окна).
- Никаких абстракций, зависимостей и «заготовок на будущее» без запроса. Удаление лучше добавления.
- Самая короткая правка не в том месте — это второй баг, а не экономия.
- Упрощение с известным пределом помечай комментарием `ponytail:` — что упрощено и как улучшить.
- **Не экономить на:** деньгах, скидках, баллах, остатках (точность важнее краткости), проверке ввода, защите от потери данных, правах доступа, доступности (размер нажимаемой области), необратимых действиях.
- Нетривиальную логику проверь коротким запуском (например, скриптом на `node`) и укажи результат в коммите.

## 4. Дизайн и удобство

Приложение — рабочий инструмент владельца и сотрудников: важны ясность, скорость и предсказуемость. Навыки в `.claude/skills/`:
- **apple-design** — принципы Apple для интерфейсов и движения. Примеры в нём написаны для веба: переводи принципы на React Native по разделу 5.
- **frontend-design** — для осмысленных визуальных решений. **Палитру и шрифты проекта он не перебивает.**

Для любой задачи по интерфейсу прочитай оба.

**Единый визуальный язык (не вводи новые цвета и шрифты без согласования):**
- Палитра: фон `#060608`, поверхности `#0e0f11` / `#141618`, текст `#ddd8d0` / `#4a4d54`, акцент — оранжевый (главное действие), зелёный (успех), фиолетовый / синий (второстепенное). Брать из `constants/theme.js`.
- Карточка: `borderRadius: 16, borderWidth: 1, borderColor: colors.border, backgroundColor: colors.surface`.
- Альбомная «список + панель»: слева `width: '38%', maxWidth: 480`, справа `flex: 1`, обе с `margin: 12` (стыкуются).
- Портретный сброс карточных стилей: `{ width: undefined, flex: 1, margin: 0, borderRadius: 0, borderWidth: 0 }`.
- Готовится полный визуальный редизайн «Смена» (строгая структура + тёплые дружелюбные цвета, геометрический шрифт для структуры и округлый для тепла). До утверждения самовольно палитру не менять.

**Восемь принципов (коротко, как проверка любого решения):**
1. *Цель* — каждый элемент оправдывает своё место; решай, что **не** делать.
2. *Свобода выбора* — давай выбор и лёгкую отмену. Подтверждение — только для необратимого, иначе оно приучает нажимать не читая.
3. *Ответственность* — действуй в интересах пользователя; риск перевешивает пользу — убери.
4. *Привычность* — одинаковое выглядит и работает одинаково, лежит в одном месте.
5. *Гибкость* — планшет и телефон, альбомная и портретная ориентации, разный опыт пользователей.
6. *Простота ≠ минимализм* — на экране одно главное действие; частое вперёд, редкое на уровень глубже.
7. *Мастерство* — ничего случайного: каждый отступ и время анимации можно объяснить.
8. *Радость* — следствие остальных семи, а не украшение.

**Правила удобства:**
- Отклик на нажатие мгновенный, а не после отпускания. Не блокируй ввод во время анимации, если можно не блокировать.
- Нажимаемая область не меньше 44 px (`hitSlop`, если элемент мал).
- На каждом экране ясно: где я, куда можно, как выйти.
- Названия — конкретные («Накладные расходы»), а не общие («Данные»). Ошибка говорит, что случилось и что делать.
- Нельзя хардкодить числа, которые считаются (например, «из 6» при 7 шагах): бери из данных.

## 5. Движение и анимации в React Native (наша практика)

- **Пружины:** критическое демпфирование (без перелёта), отклик 0,30 с: `stiffness = (2π / отклик)²`, `damping = 2·√stiffness`, `mass: 1`, `overshootClamping: true`, пороги покоя `restDisplacementThreshold: 1`, `restSpeedThreshold: 30`. Отскок — только если жест нёс импульс (бросок).
- **Скорость пальца** — в пружину при отпускании. `PanResponder` отдаёт `vx` в px/мс, пружине нужны px/с (умножай на 1000).
- **Решение «листать или вернуть»** — по проекции инерции: `dx + vx·1000·0,99 / (1 − 0,99) / 1000`, а не по точке отпускания.
- **Нативный драйвер** — для `transform` и `opacity`. Размеры и раскладку **не** анимируй JS-драйвером кадр за кадром: JS пересчитывает вёрстку всего экрана, получается дрожание. Для высоты — `LayoutAnimation`. В Expo SDK 56 включена новая архитектура: `LayoutAnimation` работает сам, а вызов `UIManager.setLayoutAnimationEnabledExperimental` там ничего не делает и пишет предупреждение — не добавлять.
- **Карусели:** не подменяй содержимое страниц в конце анимации и не сбрасывай сдвиг в ноль (это даёт «доскок»). Давай страницам постоянные номера: сдвиг страницы N = общий сдвиг + N·ширина (`Animated.add`), общий сдвиг просто едет к цели и остаётся там. Тяжёлые обновления (загрузка данных, перерисовка экрана) — после окончания анимации.
- **Размеры экрана — живые:** `useWindowDimensions`, а не `Dimensions.get` на уровне модуля (после поворота значение остаётся старым).
- **`PanResponder`** замыкает состояние первого рендера: актуальное читай через `ref` или пересоздавай объект на каждом рендере.
- **`scrollTo` сразу при появлении списка ненадёжен:** позиционируй, когда содержимое измерено (`onContentSizeChange`), и повторяй при смене ширины. Для страниц — `snapToInterval`, а не один `pagingEnabled`.
- **Модальные окна:** ширину «коробки» окна не задавай процентами от экрана — для этого есть обёртка `components/FitView.js` (телефон портретно 94%, планшет — как задумано). Окна с полями ввода оборачивай в `components/KeyboardSafe.js`.

## 6. Архитектура (главное)

- `App.js` — навигация и регистрация экранов. `db/database.js` — таблицы и миграции (каждая в `try/catch`, повторяемые). `db/queries.js` — вся логика запросов к SQLite. `db/supabase.js` — облако только для онлайн-записи. `db/session.js` — сессия и права: `can(key)`. `db/events.js` — простая подписка/уведомление между экранами.
- **Права:** `can(key)` для администратора всегда `true`; для остальных — только явно разрешённое (`perms[key] === true`) по `users.permissions` (JSON) поверх `DEFAULT_PERMISSIONS`. Если права не загружены или такого ключа нет — доступа нет (по умолчанию закрыто). Новое право обязательно добавляй в `DEFAULT_PERMISSIONS`, иначе оно будет закрыто для всех, кроме администратора. Меню фильтруется двумя независимыми фильтрами: `module` (включён ли раздел в бизнесе) и `perm` (есть ли право у сотрудника).
- **Вход и PIN (`db/userAuth.js`, `db/pinCrypto.js`).** Стартовых сотрудников и PIN нет: пока в базе нет ни одного сотрудника, открывается только мастер регистрации (`OnboardingScreen`), где администратор сам задаёт PIN. PIN нигде не хранится: в `users.pin_hash` лежит отпечаток (PBKDF2-SHA256 из `@noble/hashes` с солью бизнеса из `app_settings.pin_salt`; случайные числа — `expo-crypto`; колонка `users.pin` всегда пустая). Вход — по одному PIN из 4–6 цифр, поэтому PIN уникален среди сотрудников и не может быть простым (1234, 0000, 1212). Подбор ограничен блокировкой: после 5 неверных попыток подряд — пауза 30 с, дальше удваивается до 30 минут (счётчик в базе). Нельзя удалить, деактивировать или понизить последнего активного администратора. **Управлять сотрудниками, их ролями, правами и PIN-кодами может только администратор** (проверяется в `db/userAuth.js` по роли из базы, а не только на экранах; сотрудник свой PIN не меняет — его задаёт администратор; единственное исключение — мастер регистрации при пустой базе). Опасные действия («Стереть всё», восстановление из копии, удаление сотрудника) доступны только администратору и требуют его PIN (`PinConfirmModal`, общий счётчик неудач со входом). Автоблокировка (`components/LockGuard.js`): экран входа показывается поверх приложения в отдельном окне через заданное время без касаний (по умолчанию 5 мин, настройка `auto_lock_minutes`, только администратор) и после ухода в фон больше чем на минуту; тот же сотрудник возвращается на тот же экран, другой — на стартовый экран своей роли. Списки сотрудников (`getUsers`, `getAllUsers`) и сессия не содержат `pin` и `pin_hash`. Текущий PIN показать нельзя — только задать новый (пустое поле при правке = «не менять»).
- **Панели без своей верхней полосы** лежат в `components/panels/` и встраиваются в объединённые экраны (Финансы — 4 вкладки, Товары / Склад).
- **Вкладки вместо отдельных экранов**, где разделы логически связаны.
- **Интерактивные туры** (`TourGuide`, `TourRegistry`, `useTourHighlight`): сделаны для Кассы, Обзора, Расходов. Не сделаны: Продажи, Клиенты, Записи.
- **Записи:** онлайн (Supabase) и «по телефону» (локально) — два независимых источника; календарь общий, точки двух цветов (оранжевый — онлайн, фиолетовый — по телефону); тап по дню фильтрует список на месте. Календарь держит фиксированные 5–6 строк по числу недель месяца; карточка высотой по текущему месяцу.
- **Скидки:** «На товар» (общий процент + товары-участники) и «На заказ» (лестница: скидка клиента → ручная скидка кассира). Товар с выключенной «Скидкой на товар» исключается из базы скидки на заказ полностью (так решил владелец).
- **Онлайн-запись:** публичная страница бронирования — отдельный проект (`struktura-booking`, GitHub Pages), не в этом репозитории.

## 7. Грабли, на которые уже наступали

1. Если у элемента уже есть `borderRightWidth` / `borderLeftWidth`, общий `borderWidth` его не переопределяет — задавай все четыре стороны.
2. Тень (`shadow` / `elevation`) обрезается `overflow: 'hidden'` родителя — для разделения внутри такой карточки используй другой оттенок фона.
3. `layout.width` в `onLayout` — внешняя ширина, без учёта собственного `padding`; для точной внутренней измеряй вложенный элемент.
4. `Animated.spring` не всегда точно достигает цели к моменту вызова обратного вызова — если нужна точная позиция, принудительно `setValue(цель)`.
5. `Animated.Value.setValue` с нативным драйвером меняет нативный слой мгновенно, в обход отрисовки JS — отсюда доскоки при смене содержимого. Лучше схема без сброса (см. раздел 5).
6. Переключатель в форме с общей кнопкой «Сохранить» может выглядеть рабочим, но не сохраняться. Влияющее на работу прямо сейчас (например, на кассу) сохраняй сразу.
7. Массив данных, построенный в теле компонента из переменных, объявленных ниже в файле, даёт `ReferenceError` — порядок объявления важен.
8. Количество строк в календарной сетке зависит от месяца (5 или 6) — учитывай при расчёте высоты.
9. `Toggle` не принимает свой `hitSlop` снаружи (зашито 10) — передача игнорируется.
10. Вложенный `Pressable` внутри строки-`Pressable` в React Native работает штатно: внутренний перехватывает нажатие.
11. Результат `addUser` / `updateUser` / `deleteUser` всегда проверяй (`res.ok`) и показывай `res.error`: раньше экраны игнорировали его и писали «Сохранено» при занятом PIN.
12. Форма и экран входа должны допускать одинаковую длину PIN (4–6 цифр): раньше формы разрешали 4–6, а вход принимал ровно 4, и PIN из 5–6 цифр войти не позволял.
13. Ключ права в `can('…')` должен совпадать с `DEFAULT_PERMISSIONS`: опечатка `add_expense` вместо `add_expenses` годами означала «право не проверяется».
14. Нельзя сбрасывать `app_settings` без `pin_salt`, если сотрудники остаются: без соли отпечатки не сойдутся и никто не войдёт (`resetDatabase` это учитывает).

## 8. Безопасность и доступы

- Токены, пароли и ключи — **никогда** в файлы, коммиты, комментарии, ответы. Если токен попал в текст, скажи об этом и посоветуй перевыпустить.
- **Резервные копии:** файл копии содержит все данные бизнеса, поэтому он ВСЕГДА шифруется паролем (`db/backupCrypto.js`: AES-256-GCM, ключ из пароля — PBKDF2-SHA256, 100 000 итераций; пароль не короче 10 символов с заглавной и строчной буквой, цифрой и спецсимволом; формат `struktura-backup` версии 2). Сохранять, отправлять и выводить результат `exportAllData()` иначе как через `encryptBackup` нельзя — ни в файл, ни в «Поделиться», ни в журнал. Выгружать и восстанавливать копию может только администратор после ввода PIN. Старые копии без пароля восстановить можно (с предупреждением), новые без пароля не создаются. Автокопирование данных Android в Google Диск выключено (`allowBackup: false` в `app.json`; в сборку APK попадает после пересборки).
- **PIN-коды:** никогда не хранить открытым текстом, не логировать, не показывать, не добавлять стартовых PIN и «PIN по умолчанию». Новые места, где создаётся или меняется PIN, обязаны идти через `addUser` / `updateUser` (они проверяют длину, простоту и уникальность).
- Ключи Supabase уже зашиты в `db/supabase.js` и используются только для онлайн-записи — не расширяй их использование.
- Если онлайн-запись «перестала работать» — сначала проверь, не приостановлен ли бесплатный проект Supabase.
- Персональные данные клиентов и чеки (54-ФЗ, 152-ФЗ) — не логировать и не выносить в публичные места.

## 9. Открытые вопросы (по состоянию на конец сессии)

- Онлайн-запись: ошибка подключения к Supabase и «ссылка не найдена» по QR — причина не установлена (возможны приостановка проекта или правила доступа).
- Товары с «переменным списанием» не участвуют в товарной скидке.
- Экспорт самого отчёта (кнопку «Экспорт» в Отчётах убрали: она выгружала всю базу открытым текстом). Если понадобится — делать отдельно и только с данными отчёта.
- Безопасность: привязка отпечатков PIN к ключу устройства (`expo-secure-store`) сознательно не делалась — при зашифрованной копии выгода небольшая, а риск потерять вход при переустановке большой.
- Туры для Продаж, Клиентов, Записей.
- Фискализация (54-ФЗ): очередь чеков и сборка чека готовы, отправки в облачную кассу нет — это отдельный крупный этап вместе с собственным сервером.
- Мобильная версия (телефон как дополнение) — после основных багов планшета.
